# Re-platform plan: chat.masonjames.com on current chat-js

Companion to [ADR 001](adr/001-chatjs-replatform-and-paid-access-bridge.md). Mason answered the decisions listed at the end of the ADR on 2026-10-28 (every recommendation accepted); the answers are recorded in the ADR's status and decisions sections. The ADR status line lists amendments made after that acceptance; phases 1 to 4 do not start until Mason approves them, because the amended decision 12 file list drives phases 1 and 2 as well.

## Ground rules for every phase

- Each phase runs in its own git worktree cut from the branch it targets, with the model the phase names. Mechanical phases go to Codex (`codex exec -m gpt-6.1-sol -c model_reasoning_effort=high` for medium work, `-m gpt-6-astra -c model_reasoning_effort=medium` for the hard parts). The orchestrating session reads every delegated diff, reruns the gate itself, and requests a tool-disabled Opus 5.5 review of the packet before the PR is opened. The review context names this ADR and the phase's done criteria; the review's model, revision and verdict line go in the PR body.
- Commits are GitHub-signed through the GraphQL commit helper; nothing is pushed with a local signature. One PR per phase; Mason merges. No phase deploys, provisions, reads production environment files, or contacts a customer.
- The gate is the fork's Dagger module (`dagger call check`, then `dagger call smoke` once the image exists), adapted in phase 1 to the new layout. Until phase 1 lands, the gate is upstream's own commands run in the worktree: `bun install --frozen-lockfile`, `bun run test:types`, `bun run --cwd apps/chat test:unit`, and the native lifecycle steps from upstream's `native.yml` against a disposable PostgreSQL 17.
- Sizes: S is under half a day of build time, M is one to two days, L is three or more.

## Phase 0: new root and fork skeleton

- Size: M. Builder: Codex Sol (high). Reviewer: Opus 5.5.
- Branch `replatform/main`, created on GitHub at upstream `76fedbed` (upstream's own commits, unmodified; the fork's old history stays on today's `main`).
- Adds, as signed commits: `apps/chat/chat.config.ts` branding (app name, URL `https://chat.masonjames.com`, organization and legal copy, `authentication` flags per decision 6, `desktopApp.enabled: false`, `services.hosting: "Hetzner (Dokploy on Docker Swarm)"`); `README.md` fork notice; `docs/adr/001-...`, `docs/replatform-plan.md`, a rewritten `docs/deployment.md` skeleton; `scripts/check-fork.ts` rewritten to assert the new contract (no Stripe, Resend or Ghost dependency in the root and app manifests, no magic link or password sign-in in `lib/auth.ts`, every provider in the evaluated config off, documents present, migration journal equal to upstream's history plus contiguous fork entries; the "membership plugin present" and "R2 adapter selected" assertions are added by phases 3 and 2 when those files exist). No upstream workspace or workflow is deleted: deleting an upstream file turns every later upstream edit of it into a modify/delete conflict. Upstream-only workflows (`release.yml`, `electron-release.yml`, `docs.yml`, `preview-database-cleanup.yml`, `uiverify-chat.yml`, `uiverify-create.yml`, `uiverify-docs.yml`, `uiverify-registry.yml`, `uiverify-upload.yml`) stay in the tree and are disabled in the repository's Actions settings instead.
- Tests and gate: upstream `test:types` and `apps/chat` unit tests pass in the worktree; `scripts/check-fork.ts` and its `--self-test` pass; `bun run --cwd apps/chat check-env` is run and its output reconciled with the environment table in `docs/deployment.md` (on this root it reports the provider, storage and sandbox requirements that phases 1 to 3 change; see the deployment doc).
- Done when the PR is open with the gate lines in its body, and the ADR and plan live on the new root.
- Attended steps (Mason): Runs of the pull-request-triggered upstream workflows on phase PRs are accepted, with this evidence from the files on the root: `uiverify-chat.yml`, `uiverify-create.yml`, `uiverify-docs.yml`, `uiverify-registry.yml`, `uiverify-upload.yml` and `preview-database-cleanup.yml` each declare `permissions: contents: read` (plus read-only `actions` and `pull-requests` where they need them), so their `GITHUB_TOKEN` cannot push or comment, and their secrets are absent; `docs.yml` has no permissions block but only checks out, installs and runs `turbo run docs:links build`. `release.yml` and `electron-release.yml` run on push to `main` with the default write token and `changesets/action`; both are registered on today's default branch, so Mason disables them in the repository's Actions settings before the rename (the session that prepared phase 0 asked to do this and was refused by its permission policy, so it stays with Mason). The other seven can be disabled by file name once GitHub has registered them, which happens when they first run on a phase PR or when they reach the default branch; Mason disables them right after the rename at the latest (`uiverify-upload.yml` is a `workflow_run` workflow that does not run on phase PRs before the rename, and `preview-database-cleanup.yml` is `pull_request_target`). After merge review, rename `main` to `legacy-main`, promote `replatform/main` to `main` and make it the default branch. Phases 1 to 4 target `replatform/main` until the rename, then `main`.

## Phase 3: the membership bridge plugin

- Size: L. Builder: Codex Astra (medium). Reviewer: Opus 5.5, with the review context pointing at decisions 2, 4, 5 and 7 and asking specifically for replay, expiry, audience, clock-skew and double-grant failure paths.
- `apps/chat/plugins/membership/` with `chatjs.json` (billing export, router, account summary), `schema.ts` (balance with a default of 0 cents, `Membership`, `MembershipHandoff`, `MembershipGrant`), `billing.ts` (`canSpend` true only when the balance is positive and the snapshot is unexpired with at least one allowlisted plan slug; `debit`), `handoff.ts` (Ed25519 verification, nonce single use, payload schema with Zod), `auth-plugin.ts` (Better Auth plugin endpoint `/paid-access/callback` that verifies the token, upserts the user and snapshot, creates the session and redirects to the chat's own `/`, a fixed target, never to a caller-supplied URL), `allowances.ts` (an allowlist from plan slug to monthly cents; unknown slugs and `free` grant nothing; it ships empty until Mason states the cents per slug in writing for this PR), `grants.ts` (idempotent monthly grant on first request), `router.ts` (balance, membership status, expiry), `account-summary.tsx`, `cleanup.ts` (expired nonces), an extension of `scripts/validate-env.ts` that requires `MEMBERSHIP_HANDOFF_PUBLIC_KEY` and checks that it parses as an Ed25519 public key, and a sign-in button in `components/auth-providers.tsx` that sends the member to `https://masonjames.com/account/chat/` after setting the `__Host-` prefixed handoff state cookie (ADR decision 2). The callback accepts the token only by POST. Uninstall the upstream `credits` plugin (`plugins/credits/**` is deleted; see ADR decision 12 for the conflict rule). Migration `0022_membership_bridge` and journal entry. Three lines in `lib/auth.ts`: registering the auth plugin, `https://masonjames.com` in `trustedOrigins` because the callback is a cross-origin POST, and the `mjchat` cookie prefix. The site handoff URL and the token audience (the chat origin, exactly `https://chat.masonjames.com` in production) live in `plugins/membership/config.ts`, derived from `APP_URL`, so `chat.config.ts` and its schema are untouched.
- Tests and gate: unit tests for every rejection path (bad signature, wrong audience, expired, future-dated beyond a 60-second skew, reused nonce, unknown issuer, a GET request, a state cookie that does not match the token's nonce), for the allowance ledger (two concurrent first requests grant once), for `canSpend` with expired and lapsed snapshots and with a positive balance but no allowlisted plan; for the allowance rules that an unknown slug grants nothing, `free` grants nothing, an empty allowlist grants nothing, and a second grant in the same period never adds (the balance is set to the maximum, not summed); for a member with two allowlisted plans receiving the largest allowance, not the sum and not the first; for an upgrade granting the difference up to the larger allowance; for a downgrade and for a sideways change to an equal allowance granting nothing even after the balance was spent; for the state cookie being `__Host-` prefixed and exactly 43 base64url characters; for the post-sign-in redirect staying `/` whatever the callback's fields, query or Referer carry; for a freshly handed-off allowlisted member with a 0-cent balance being admitted on the first request with the grant recorded once; for `canSpend` never being consulted for an anonymous guest turn (confirmed against core's admission path); `validate-env` fails without `MEMBERSHIP_HANDOFF_PUBLIC_KEY` or with a key that is not Ed25519; the Dagger `check` migration rehearsal applies `0022` on an empty database and again as a no-op; `smoke` sends a forged token and expects 401.
- Done when the PR is open with the test counts, the gate lines and the Opus verdict line.

## Phase 4: site side (masonjames.com)

- Size: S. Builder: Codex Sol (high). Reviewer: Opus 5.5. Separate PR in `masonjames/masonjames.com`; starts only after Mason confirms that repository may be changed for this work.
- `emdash-site/src/pages/account/chat.astro`: requires a Paid Access session (redirects to sign-in otherwise), reads `Astro.locals.paidAccess.segments()`, reads the chat's handoff state value from the query string (exactly 43 base64url characters, else 400), mints the token with the Ed25519 private key from `CHAT_HANDOFF_PRIVATE_KEY`, the audience set to the chat origin from `CHAT_HANDOFF_ORIGIN` (exactly `https://chat.masonjames.com` in production, the same string the chat derives from `APP_URL`), and that state echoed as `nonce`, and renders an auto-submitting POST form to the chat callback with `Cache-Control: private, no-store` (never a redirect, so the token is never in a URL). Tests in `emdash-site/scripts/` for the token shape and for the route's response: a POST form to the chat callback, no `Location` header, `Cache-Control: private, no-store`, and the token absent from the URL. The "Member chat" navigation link stays as it is. A member without a Paid Access session is sent to the site's sign-in and, after the magic link, lands on the account page; the chat's login page tells them to press its button again, which issues a fresh state; the site's sign-in return URL never carries `state`, so a token is never minted for a state that did not come straight from the chat's button.
- Tests and gate: the site's existing test and lint commands; a shared fixture token verified by the chat's phase 3 tests so both sides agree on the format.
- Done when the PR is open and the public key for the chat is recorded in the deployment doc (the private key never leaves the site's secrets).

## Phase 5: attended provisioning and cutover (Mason, with Dockhand where it applies)

Nothing here is done by an agent. Each item is one approval.

1. Neon: new project, one database, autosuspend set for the persistent workflow listener; record the pooled URL as `DATABASE_URL` and the direct URL as `DATABASE_MIGRATION_URL` and `WORKFLOW_POSTGRES_URL`.
2. R2: new bucket or prefix with private access; API token scoped to it.
3. Secrets: generate `AUTH_SECRET`, `EVE_GATEWAY_SECRET` (32+ chars), `CRON_SECRET`, the Ed25519 key pair (private to the site, public to the chat); reuse the Vercel AI Gateway key; store all in Dokploy's managed environment, never in the repository.
4. platform-infra: new governed manifest with the new environment contract, the `/api/health` check, `stop-first` update order, the cleanup service, and `SPARKA_IMAGE` pinned to the digest `dagger call publish` returns for the merged `main`; catalog row updated (`health_contract` HTTP check `/api/health`, dependencies drop Resend, `update_sources` unchanged). PR in platform-infra; Mason merges.
5. Dokploy: new project and Compose service from the manifest on a staging hostname first (for example `chat-next.masonjames.com`); run the one-shot `bun run --cwd apps/chat setup` in the image against the new database; verify `/api/health` 200, a handoff from the site using a staging key pair and the staging origin as audience (the site's `CHAT_HANDOFF_ORIGIN` and key are switched for the test and back; the audience check is never loosened), a streaming chat, an attachment upload and download, and the hourly cleanup call.
6. Cutover: point `chat.masonjames.com` at the new service in Dokploy and Caddy; keep the old manual Compose service running but unrouted for the rollback window. Rollback is repointing the route back; the databases are separate so no data step is involved.
7. Re-pointing webhooks: none to re-point. Delete the Stripe webhook endpoint that targeted `/api/webhooks/stripe` and the Ghost webhook that targeted `/api/webhooks/ghost` in their dashboards; revoke the Resend key and the legacy OAuth app callbacks that are no longer used.
8. After the rollback window: remove the legacy Compose service, delete the old Neon database after the retention period Mason chose, and update the platform-infra catalog evidence.

- Size: S. Builder: Codex Sol (high).

## What is explicitly not carried over

Listed in ADR decision 14: Ghost and Stripe bridges, magic link and password sign-in, cookie sharing and `/api/auth/validate`, the entitlement tables and router, all chat and credit data, existing R2 objects, the Node 22 standalone image and entrypoint migrations, Redis, and the legacy Compose source on platform-core.

## Risks to watch

- Upstream moves fast (902 merged PRs); phases 1 to 3 should each start by fast-forwarding the worktree to the latest upstream-rooted `main` so the bridge never targets a stale tree.
- The Better Auth internal session API is used by upstream's own magic-link plugin, but the exact helper names are verified at phase 3 build time against the installed version.
- The callback is a cross-site form POST (`application/x-www-form-urlencoded`) into a Better Auth plugin endpoint; whether Better Auth parses that body and how its origin and CSRF checks treat it is verified at phase 3 build time, with a plain Next route in front of the plugin as the fallback.
- Neon scale-to-zero and the workflow listener (ADR decision 9).
- Guest access stays off until the Caddy single-IP header contract is verified; this is a feature loss compared to today's anonymous mode and is accepted for the proof of concept.
